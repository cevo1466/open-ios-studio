# Swift language support (sourcekit-lsp) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Completion, hover and inline diagnostics for Swift files from `sourcekit-lsp`, started per workspace through the Rust backend, with the diagnostics also listed in the Sorunlar tab and a status-bar segment that says what the server is doing.

**Architecture:** Rust spawns `sourcekit-lsp` with stdio pipes (no shell, allow-listed environment, workspace cwd), relays `Content-Length` frames to the webview over a Tauri channel and writes frames the webview sends. A small TypeScript JSON-RPC client drives `initialize`, document sync, completion and hover; Monaco providers and markers are registered once per editor mount. Build settings come from xtool's own `.bsp/xtool.json` (sourcekit-lsp launches `xtool dev build-server` itself); the Studio writes no config file.

**Tech Stack:** Rust std::process + thread reader (no new crates), Tauri `Channel`, TypeScript, Monaco providers, Vitest, Playwright (fake `lsp_*` commands), a 60-line Python fake LSP server for the Rust test.

**Spec:** `docs/superpowers/specs/2026-11-03-launch-readiness-2-design.md`, section "3. Swift language support".

## Global Constraints

- Program resolution: `sourcekit-lsp` on the widened PATH (`cli_ai::find_program`), else next to the `swift` binary. Missing → `lsp_start` returns `Err("sourcekit-lsp was not found")` and the UI shows `Swift LSP: yok`.
- One session per workspace; `lsp_stop` before `lsp_start`; a workspace change stops it.
- Frames: `Content-Length: N\r\n\r\n<json>`; max 16 MB per frame (larger → session error + stop); reader thread, bounded by the channel.
- Status labels (exact): `Swift LSP: çalışıyor`, `Swift LSP: Linux hedefi`, `Swift LSP: yok`, `Swift LSP: başlatılıyor`, `Swift LSP: durdu`.
- `Linux hedefi` when the server runs without `.bsp/xtool.json` in the workspace root; its tooltip: `Proje xtool build server tanımlamıyor; iOS'a özel API'ler hata olarak görünebilir.`
- Diagnostics mapping: LSP severity 1 → `error`, 2 → `warning`, 3/4 → `note`; lines 1-based; `source` shown as `sourcekit-lsp` in the Problems list text; LSP rows do not change the build "errors/warnings" counts in the status bar (they are shown as a separate count in the Problems tab badge: `N LSP`).
- Document sync: full text, 300 ms debounce on `didChange`, in-flight completion requests are cancelled by ignoring stale responses (request id compare).
- Only `.swift` files are sent to the server.
- Do not touch `terminalInput.ts`, `TerminalPanel.tsx`, `UpdatesSection.tsx`.

## Review Focus

- The server crashing mid-session (EOF on stdout): status `durdu`, no stuck promises (Task 2 `rejectAll` test; Task 1 exit event test).
- A frame larger than 16 MB from the server: the parser errors instead of growing unbounded (Task 1 test).
- Two quick keystrokes: only one `didChange` after the debounce, with an increasing version (Task 3 unit test of the debouncer).
- A completion response arriving after the user moved on: ignored, no crash (Task 2 stale-id test).
- Opening a non-Swift file must not send `didOpen` (Task 3 E2E asserts no `lsp_send` with `Package.swift`? Note: `Package.swift` IS Swift; the E2E uses `xtool.yml` for the negative case).

- `pub struct FrameParser` with `push(&mut self, bytes: &[u8]) -> Result<Vec<String>, String>` (returns complete JSON payloads; error on missing/invalid `Content-Length` or a frame over `MAX_FRAME` = 16 MiB).
